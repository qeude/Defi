# macOS window surface transitions: feasibility research

**Question.** Can Defi get a near-imperceptible continuous ribbon/overview handoff at low RAM and CPU by animating cached graphics proxies, while ordinary managed windows remain native?

**Research date:** 2026-10-03. Primary-source research and a bounded Defi prototype; measurements below describe this machine and workload only.

## Current finding

The implemented path uses bounded one-shot ScreenCaptureKit snapshots for Overview
and native Accessibility motion for ordinary ribbon navigation. The opt-in ribbon
representation experiment reuses those snapshots; it does not keep persistent
streams. The stream and disk-cache proposals below are earlier hypotheses,
superseded by the prototype correction later in this document.

## Initial hypothesis

The strongest low-risk experiment is a public ScreenCaptureKit prototype that captures only the currently relevant windows, retains at most the latest IOSurface per selected window, and displays that surface in a Defi-owned Metal/AppKit proxy during the handoff. Keep the proxy available before motion starts, then hand off to the real window at the endpoint. Do not start a capture stream for every window by default. Apple explicitly describes ScreenCaptureKit output as IOSurface-backed, uses idle status to indicate no new surface, and documents a default queue depth of three with a hard recommendation not to exceed eight. Each held surface reduces the producer's available surface pool; that bounds buffering but does not establish the cost of many simultaneous streams. [Apple's capture sample](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos?language=objc), [WWDC22: Meet ScreenCaptureKit](https://developer.apple.com/videos/play/wwdc2022/10156/), [queueDepth](https://developer.apple.com/documentation/screencapturekit/scstreamconfiguration/queuedepth)

This is a plausible way to make a transition visually continuous, not evidence that it will be imperceptible. The proxy can be rendered and moved by Defi without waiting on the other app's Accessibility lane, but it is a frozen image unless refreshed. A stale image, missing menus/tooltips, capture permission, fullscreen behavior, and replacement timing at the endpoint all need an actual prototype. A fresh image at the exact handoff may itself be too slow.

## What public APIs establish

- `SCStream` is Apple's public API for capturing display or window content. A single-window `SCContentFilter` is supported, and Apple's WWDC example explicitly discusses window capture when the source is resized, occluded, moved off-screen, or minimized. This makes a prototype feasible even when a window is not currently unobscured; it does not promise every app/window type works identically. [SCStream](https://developer.apple.com/documentation/screencapturekit/scstream?language=objc), [WWDC22: Take ScreenCaptureKit to the next level](https://developer.apple.com/videos/play/wwdc2022/10155/?time=276), [SCContentFilter including windows](https://developer.apple.com/documentation/screencapturekit/sccontentfilter/init%28display%3Aincluding%3A%29?changes=l_1_1_8&language=objc)
- Apple's sample gets the `CVPixelBuffer` from the `CMSampleBuffer`, then obtains the backing `IOSurface`. The surface can be placed in an `NSView` layer. The WWDC session says a complete status is a new frame and idle means the content did not change, so there is no new IOSurface. These facts support holding the latest surface and reusing it without making a CPU bitmap copy on every animation frame. Apple's published sample uses a layer; Metal texture import/rendering is a reasonable implementation hypothesis, not demonstrated by those cited lines as a complete capture-to-Metal proxy pipeline. [Apple sample](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos?language=objc), [WWDC22 session transcript](https://developer.apple.com/videos/play/wwdc2022/10156/)
- The framework is designed for high-performance capture and uses GPU acceleration, but requires the user's Screen Recording consent. Persistent ScreenCaptureKit streams expose system capture-awareness UI. The one-shot experiments use existing access without requesting permission; transient indicator behavior for one-shot captures remains unverified. [ScreenCaptureKit overview](https://developer.apple.com/documentation/ScreenCaptureKit?language=objc), [WWDC23 privacy session](https://developer.apple.com/videos/play/wwdc2023/10053/?time=344)
- `queueDepth` defaults to three; Apple says deeper queues use more memory, and explicitly says not to exceed eight. WWDC describes the surfaces as a server-side pool and says retaining surfaces reduces the remaining pool; if they are not released quickly enough, capture stalls and drops frames. Hence retain no capture history in RAM. A full 3840×2160 BGRA surface is about 31.6 MiB before row alignment; at 2560×1600 it is 15.6 MiB. Three pool surfaces per stream are roughly 95 MiB and 47 MiB respectively, as a raw-size estimate, before compositor/GPU overhead. Multiple streams multiply that order of magnitude. [queueDepth](https://developer.apple.com/documentation/screencapturekit/scstreamconfiguration/queuedepth), [WWDC22: Take ScreenCaptureKit to the next level](https://developer.apple.com/videos/play/wwdc2022/10155/)
- Apple warns that frequently changing stream output dimensions can cause additional allocations and is not recommended. Keep a stream's dimensions stable, or recreate it at deliberate lifecycle boundaries rather than resizing it continuously with the ribbon. [WWDC22 single-window capture discussion](https://developer.apple.com/videos/play/wwdc2022/10155/?time=276)

## Cost and storage recommendation

Favor a **disk-backed, compressed thumbnail cache plus a tiny RAM working set** if Defi needs proxies for many windows. Keep the current/next window's newest surface (or one scaled proxy surface) in RAM; release IOSurfaces promptly; store occasional compressed snapshots on disk and decode lazily before navigation. Disk costs capacity and occasional decode latency, while uncompressed full-resolution IOSurfaces cost tens of MiB each. The disk proposal is an engineering inference; Apple does not prescribe a window-manager cache policy.

For a 60 Hz ribbon, do not encode/decode from disk on the animation path. Warm likely-next proxy surfaces before a navigation gesture if cheap, but bound that speculation to one or two candidates. For a genuinely live proxy, test one persistent stream for the selected/current window first. Only expand to nearby windows after measurement. A 1–5 fps stream may keep snapshots fresh during idle at much lower nominal throughput than 60 fps, but frame rate alone does not prove low CPU, low power, or absence of ScreenCaptureKit/WindowServer problems.

Avoid a short-lived `captureSampleBuffer` stream for each transition. AltTab maintainers reported that on macOS 26, their repeated one-shot capture path caused WindowServer instability; they described persistent per-window streams as the intended zero-copy option but cautioned that many always-running streams have CPU/power costs. That is first-party project experience, not an Apple guarantee, and applies to the reported versions/path. [AltTab issue #5786](https://github.com/lwouis/alt-tab-macos/issues/5786). A separate AltTab issue reports a 30 fps refresh prototype using private `CGSHWCaptureWindowList` was already laggy and failed to reach 60 fps, and investigated a private `SLSHWCaptureStreamCreateWithWindow`; it does not prove that private stream API is usable or stable. [AltTab issue #122](https://github.com/lwouis/alt-tab-macos/issues/122)

## Private SkyLight/CGS window mutation and ownership

Yabai's public source declares private `SLSSetWindowTransform` and related functions. A third-party CGS header documents `CGSSetWindowTransform` and claims strong transform restrictions (including no upscaling past the original frame). These are evidence that private symbols and experiments exist, not a supported contract or proof that a third-party process can apply reliable transforms to arbitrary app windows on current macOS. [yabai extern.h](https://github.com/asmvik/yabai/blob/master/src/misc/extern.h), [CGSInternal header](https://github.com/NUIKit/CGSInternal/blob/master/CGSWindow.h)

Yabai documents a separate scripting-addition path: it injects into Dock, which it says owns the sole connection to WindowServer; some advanced operations need SIP partially disabled. Its docs list particular features such as window opacity, layers, animations, and Space operations as requiring that addition. They do **not** establish that every private SkyLight transform call requires disabled SIP, nor that SIP-off grants safe or supported arbitrary proxy transforms. The precise conclusion is: private APIs may be callable in some cases with SIP enabled, but the ability to mutate arbitrary third-party windows reliably without Dock injection is not established by these sources. [yabai SIP documentation](https://github.com/asmvik/yabai/wiki/Disabling-System-Integrity-Protection/0b75fef379c579096b2a51d6a0ddeb92ebe12130), [yabai command documentation](https://github.com/asmvik/yabai/blob/master/doc/yabai.asciidoc)

Defi's own policy requires proof public APIs cannot meet a user-visible invariant before private mutation, confines it to `DefiMacOS`, and specifically approves third-party position/size mutation only for the opt-in experimental frame backend. A ribbon animation that privately scales/translates ordinary user windows would cross that policy boundary and is not the recommended path. A Defi-owned proxy window is different: Defi controls its own layer/window, and can animate it with public AppKit/Metal while the native window stays untouched. However, overlay ordering, focus, clicks, Spaces, and capture feedback still need validation.

### Specific question: `CGSHWCaptureWindowList`

There is credible implementation evidence that a normal app can resolve and call private `CGSHWCaptureWindowList` without injecting into Dock: the cmdcmd maintainer describes the symbol as `dlsym`-reachable from a normal process, documents the signature as taking a window-ID pointer plus count, and states its implementation has moved to it. The call shape accepts a list/count, so batching several windows in **one call** is a supported-by-observation experiment; the result is an array of `CGImage`s. It is not an IOSurface-returning API and its private ABI/semantics are not guaranteed. [cmdcmd issue #21](https://github.com/peterp/cmdcmd/issues/21), [cmdcmd v0.4.0 release](https://github.com/peterp/cmdcmd/releases)

The cmdcmd project reports using it for current macOS live tile previews and reports that Screen Recording permission remains required and the app remains attributed in the menu bar. That is useful evidence of a non-Dock-injected route on the author's tested setup, but **not** a guarantee for all macOS releases, OS configurations, windows, or Defi's bundle/entitlements. It also says the batch call is polled, and notes a WindowServer memory leak above roughly 30 fps. That leak threshold is an author-reported observation, not an independently reproduced or Apple-documented limit. AltTab's older 30 fps prototype likewise missed 60 fps, so this path should be measured rather than assumed fast. [cmdcmd issue #21](https://github.com/peterp/cmdcmd/issues/21), [AltTab issue #122](https://github.com/lwouis/alt-tab-macos/issues/122)

**Recommendation for Defi:** a one-shot-at-ribbon-open `CGSHWCaptureWindowList` batch is now the cheapest high-value *private* spike, if the team elects to evaluate read-only capture separately from the default product path. It avoids N stream startup and can produce an image for each window before animation. However, this captures pixel content rather than optional metadata, so Defi's private-API exception for read-only metadata does not automatically authorize it; the experimental-frame-backend opt-in exception names third-party position/size mutation, not screenshot capture. Do not silently ship this under either exception. The public control is a one-shot ScreenCaptureKit `SCScreenshotManager` capture at ribbon-open, with an explicit Screen Recording permission/failure path; it returns `CGImage`, not the capture stream's IOSurface. A single full-display capture can provide one system request, but only reflects the composited visible screen, so occluded/off-screen windows cannot be faithfully recovered by cropping it. Capturing individual windows uses a per-window filter and separate requests. [SCScreenshotManager](https://developer.apple.com/documentation/screencapturekit/scscreenshotmanager?changes=la_4_5_9&language=objc), [single-frame capture API](https://developer.apple.com/documentation/ScreenCaptureKit/SCScreenshotManager/captureImage%28contentFilter%3Aconfiguration%3AcompletionHandler%3A%29)

## Visual continuity target

The target is a continuous horizontal ribbon and an overview zoom-out in which content, title bars, clipping, and window geometry move together. The handoff between a native window and its graphical representation should preserve apparent position, scale, sharpness, stacking, and content freshness. A convincing graphics transform alone does not establish low capture latency or low memory cost; those properties require separate measurement. Captured proxies and native compositor transforms are alternative mechanisms to investigate, with the public-API and private-API constraints described above.

## Defi prototype result

The first opt-in `overview.experimental_surface_transitions` variant kept public per-window ScreenCaptureKit streams warm for the active workspace, froze their latest frames once into CGImages, and animated Defi-owned Core Animation layers between verified native bounds and overview bounds. It preserves native title bars and does not mutate native geometry for the animation. It is an overview handoff experiment, not a replacement for normal ribbon navigation. Disk caching was deliberately excluded from the handoff; compressed old thumbnails would not establish freshness at the native endpoint.

Local verification and the focused native desktop test passed with Accessibility and Screen Recording available. The test covers fresh capture, panel recreation, rapid close/reopen cancellation, unchanged native geometry, and teardown. Computer Use inspected the installed overview and a subsequent ordinary click in the native TextEdit window. Still screenshots do not establish frame-by-frame imperceptibility.

On the owned 640×440 fixture, the first run froze images in approximately 21 ms initially and 2 ms subsequently. On the installed full-height Retina TextEdit window, two opening freezes took 39.7 and 75.8 ms; estimated producer/retained buffers totaled 79.36 MiB, excluding frozen images and framework/compositor overhead. Both installed openings used the surface transition with zero fallbacks. A panel-recreation bug originally discarded warmed captures; the lifecycle fix and regression test preserve them independently of panel recreation.

After that fix, the focused native fixture test measured 9.5 and 4.5 ms. A short paired idle sample on the installed TextEdit scene reported daemon CPU at 0% with capture disabled and 1.6–2.3% enabled. Both samples reported approximately 310 MiB process footprint after earlier captures, so this does not isolate incremental RAM: retained allocations, compression, and capture surfaces outside the daemon require a longer clean-process comparison. WindowServer/replayd CPU and energy were not isolated. Verification artifacts are under ignored `dist/verification/20261003-122542-517d199e/` (local/stage), `20261003-122731-08fb8265/` (focused desktop), and `surface-computer-use/` (installed trial). Original configuration, all monitor workspaces, focus, widths, scroll, and managed frames were restored; exactly one daemon remained.

The user's ordinary multi-window workspace exceeded the 96 MiB buffer estimate and correctly used the ordinary overview fallback. Consequently this experiment does **not** yet meet the combined near-imperceptibility and low-resource requirements for the full ribbon. Shadows, live content changes during a frozen animation, cold starts, multiple displays, and total WindowServer/replayd cost remain unqualified. Small-window results must not be extrapolated to Retina workspaces.

The follow-up variant renders the retained IOSurface directly, avoiding the synchronous CGImage conversion measured above. It updates layer content at a bounded 30 Hz cadence while the overview projection is unchanged, retains no frame history, falls back to ordinary previews when that projection changes, and estimates four buffers per window (producer, callback, and display overlap) within the same 96 MiB budget. Idle frames reuse unchanged content; stream errors invalidate it. The optional controlled native test uses an owned opaque backdrop and an animated fixture. An external native display recording captures the real scene; recording/encoding adds overhead. An SCRecordingOutput attempt produced incomplete files on this setup, so it was not retained as evidence or a test dependency. Measurements of this variant must be distinguished from the first variant above. [Apple capture sample](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos), [Apple recording API](https://developer.apple.com/documentation/screencapturekit/screcordingoutput). That addresses conversion latency and copies, but does not eliminate ScreenCaptureKit's producer pools. Compare a single display capture for the visible opening scene (occluded/offscreen content requires a separate path), and a bounded lower-resolution cache for inactive cards. Private batched capture and native compositor transforms remain hypotheses, with the policy and reliability constraints described above.

## Direct-surface validation and remaining visual defect

The final full-height 640-point Retina fixture passed local verification and the focused desktop test with Accessibility and Screen Recording available. The capture reference acquisition measured 0.008–0.023 ms; this is not total opening latency. The four-buffer estimate was 54,726,144 bytes (52.19 MiB). The test verifies changing surface submissions, unchanged native geometry, panel recreation, rapid reopen, and teardown; it does not verify pixel correctness of those submissions.

Installed Computer Use inspected a real TextEdit overview surface and verified an ordinary native text-area click after closing it. Its buffer estimate was 69.63 MiB. Three short idle samples reported 0%, 1.4%, and 2.2% daemon CPU enabled, versus 0% disabled; both process footprints were approximately 280 MiB after capture, so incremental memory is not isolated. WindowServer/replayd and energy remain unmeasured.

The real 60 fps screen recording of the animated owned fixture exposes a defect: the first overview opening shows background/empty content, while the second displays the animated window. Its cause remains unresolved; live buffer submission counters alone cannot establish correct pixels. The clip retains both openings, trimming only unrelated desktop lead-in/out. Therefore this prototype is not ready to claim an imperceptible native/proxy handoff or replace normal ribbon scrolling. It stays disabled by default. Disk storage can reduce inactive thumbnail cache residency, but cannot remove decoded display surfaces or live producer buffers.

## Cheapest public experiment

1. Implement a disposable prototype path behind a feature flag: request one public ScreenCaptureKit single-window screenshot at ribbon-open, render its `CGImage` as a Defi-owned proxy, and animate that proxy. This tests the handoff with one native window and one capture, without stream setup. For many simultaneously visible windows, compare one full-display screenshot plus crops (cheap request count, but occlusion fidelity is lost) with per-window screenshots. If public one-shot latency is insufficient, switch the prototype to a single-window stream at stable reduced resolution/modest update rate and hold only its latest IOSurface. Separately compare the private batch capture spike described above only if private pixel capture is explicitly in scope.
2. Render the surface in a Defi-owned overlay/proxy and animate that proxy through a short ribbon movement while the native window remains at its original geometry. At the destination, hide the proxy and expose/focus the real window. Start with a stationary app and a typing/scrolling app to reveal stale-frame and cursor/menu differences.
3. Measure cold-start and warm-start handoff latency, frame-time misses, Defi/WindowServer/replayd CPU, power, and memory with 1, 3, then 10 windows. Compare one persistent stream against an occasional screenshot refresh. Test occluded and minimized states separately. Do not infer whole-ribbon scalability from a single window.
4. If the prototype passes, decide whether one or two recently used proxies should stay warm in RAM, while the broader snapshot cache stays compressed on disk. If it fails due to capture latency or system cost, keep the ribbon native-window-only and investigate a shorter staged transition rather than adding unbounded capture streams.

This experiment is the cheapest because it tests the pivotal assumption—whether a Defi-owned proxy can bridge the animation and focus handoff—without private window mutation, an always-on stream per application window, or a long-lived cache architecture first.


## Shared live-video ribbon and overview trial (latest implementation)

This implementation supersedes the overview-only experiments above. The opt-in path shares a bounded ScreenCaptureKit cache between normal horizontal ribbon navigation and Overview. Visible windows and at most one neighbour on each side are captured at native resolution. The current NV12 format preserves luma resolution and reduces the estimated pool size relative to BGRA, at the cost of chroma subsampling. A prewarmed AVSampleBufferDisplayLayer displays each uncompressed buffer directly; Defi performs no video encoding or per-frame CPU bitmap conversion. Readiness is checked before presentation. This public renderer supports uncompressed frames and exposes readiness for the first displayed frame. [Apple video layer documentation](https://developer.apple.com/documentation/avfoundation/avsamplebufferdisplaylayer), [Apple sample buffer renderer](https://developer.apple.com/documentation/avfoundation/avsamplebufferdisplaylayer/samplebufferrenderer).

Ribbon proxies animate together in a workarea-sized panel. The normal Accessibility coordinator commits final native positions underneath, and the panel is removed only after public native bounds and owner PIDs converge. Supersession, mouse interaction, fullscreen and display changes cancel the scene. Native focus and workspace membership remain on the existing runtime path. Cached layers reset their transforms before reuse; configured borders follow the proxies. The wallpaper is prepared before opening. Inactive cards use one-shot compact captures in the existing 32 MiB cache, without additional streams. Changed Overview projections still return to ordinary preview rendering.

Local build, non-desktop tests and workflow tests passed under `dist/verification/20261003-143355-b1404642/`. The focused native test `DesktopE2ETests/testOverviewSurfaceTransitionUsesFreshOwnedWindowAndReopensSafely` passed under `20261003-143607-27a8cfd7/`, with Accessibility and Screen Recording available. It covers animated owned-window content, ribbon/native convergence, Overview reopening, unchanged native Overview geometry, bounded capture residency and teardown. The full desktop suite was not run; desktop coverage is this focused test plus installed Computer Use and the real-window recording. Documentation was updated after these code checks.

The installed trial used the user's existing nine-window Ghostty workspace and the existing Finder/T3/Xcode workspace. The former retained four streams with a 160.31 MiB four-buffer estimate; the latter retained three streams with a 120.23 MiB estimate. The compact preview cache reported 11.22 MiB when opened. Across the recorded trial, status reported seven GPU ribbon transitions with one fallback, and five GPU Overview openings with one fallback. These are aggregate counters across recording attempts, not a count of every motion in one clip. Geometry/freshness checks intentionally permit fallback; no universal imperceptibility follows from successful counters. The real video is `dist/verification/ribbon-evidence/real-ribbon-overview.mp4` (28 seconds, 1920×1080, 60 fps), with the native Finder/T3/Xcode ribbon sequence in its second half. It includes Overview navigation and both opening/closing scenes; it is not a synthetic window fixture. Status, trace and a frame contact sheet are alongside it. One initial command sequence was corrupted by terminal input buffering; the subsequent recording used a script file. Direct Computer Use access to Ghostty remains blocked, so its visual evidence is the authorized native recording. Computer Use exercised the installed Defi panel and a normal native Finder click after closing it.

A short paired sample taken without recording/encoding found daemon CPU approximately 0–0.1% disabled versus 9.3–14.2% enabled, WindowServer 19.9–21.3% versus 55.2–57.3%, and replayd 0% versus 3.4–4.7%. These are percentages of one CPU core and short workload-specific samples, not an energy benchmark. Reported daemon footprint was about 24 versus 30 MiB, while WindowServer was about 1961 versus 2139–2168 MiB; externally hosted capture buffers make daemon footprint alone misleading. Other compositor activity and startup allocation prevent attributing the entire difference to Defi. The pool estimate is not a total memory bound. Capture preparation and renderer allocations may overlap during replacement.

The trial establishes a functioning shared ribbon/Overview surface path on ordinary current windows, but does not yet meet a production guarantee of near-imperceptibility with low total resource cost. Cold preparation, fallback openings, chroma fidelity, missing native shadows, dynamic content timing, projection changes and multiple displays remain unqualified. Disk storage would help inactive compressed thumbnails; it would not remove the live producer pools or decoded display buffers required at handoff. A measured next comparison is a single-display capture for visible content plus selective offscreen captures, versus lower idle cadence with a fresh endpoint sample; neither has been demonstrated by this implementation. Native private compositor transforms remain outside the approved public-API trial.

The original configuration, monitor workspace stack, logical focus, widths, scroll offsets and managed-frame convergence were restored after validation. The experiment is disabled by default and the tested build remains installed. Exactly one daemon is required after restoration.


## User feedback correction: snapshots for Overview, native ribbon

The user observed persistent sharing badges, flicker, and disrupted ribbon animation. Runtime feedback showed 16 GPU ribbon transitions versus 36 fallbacks, despite the quieter controlled recording. Continuous per-window streams explain the persistent capture session; Apple exposes no general documented capture-indicator suppression option. One-shot screenshots avoid maintaining such a session, but the presence of transient system UI still needs empirical validation. [SCStreamConfiguration](https://developer.apple.com/documentation/screencapturekit/scstreamconfiguration), [SCScreenshotManager](https://developer.apple.com/documentation/screencapturekit/scscreenshotmanager).

The user explicitly chose one-shot Overview snapshots and the native ribbon while the proxy ribbon is corrected. The daemon now keeps normal ribbon navigation on the native backend. The Overview cache uses public `captureSampleBuffer` screenshots instead of SCStream, refreshes at most once per second while closed, and freezes during the entire opening/session. There are no persistent capture streams. Snapshot content may lag ongoing typing or animation; this tradeoff was accepted explicitly and is not a live-content handoff guarantee.

An owned native regression reproduced a separate reuse defect: after a non-reversing close, the next Overview scene kept the prior reduced layer transform. Assigning its native frame under that transform also produced incorrect bounds (about 1268×2716 instead of 640×1371 in the fixture). The scene now resets transform, bounds and position under disabled implicit Core Animation actions. The regression failed before the correction and passed after it, also checking zero streams and one fixed displayed snapshot. This addresses a concrete source of jumps at reopening; it does not by itself prove all observed flicker is gone.


A real repeated-opening recording exposed a new snapshot-specific expiry defect: the initial opening used the surface zoom, but the next opening fell back because the cached image aged while it was intentionally frozen. An owned fixture held open for over three seconds reproduced it. Snapshot idle validity is now paused during display and resumed after closing; discovery preparation waits until the closing scene has released its texture. The long-dwell/rapid-reopen regression failed before this correction and passed afterward. This preserves the explicitly static snapshot rather than falsely describing it as newly captured content. Computer Use observed the normal Finder traffic-light buttons in place of its persistent purple capture badge, with snapshots enabled and zero streams. A short sample without recording reported daemon CPU 0.3–0.4% enabled, versus 0% disabled; WindowServer was approximately 25% versus 16.4–16.6%. These remain workload-specific short samples, not a total energy or RAM benchmark.

A subsequent abrupt-opening report reproduced a second expiry path: an idle screenshot older than three seconds was rejected even when its owner and dimensions still matched. The native regression now delays the idle refresh for 3.2 seconds before opening and requires both zoom openings to succeed. Compatible snapshots remain available until replacement; request changes still invalidate incompatible owner/dimensions and the capture pool remains bounded. This can show older content when refresh fails, but avoids a timer-driven switch to a non-zoom opening. Native ribbon navigation remains separate: its adaptive Accessibility latency guard may intentionally submit zero-duration coherent motion when a participating lane cannot produce intermediate frames safely.

Repeated real-window openings still exposed warm-up fallbacks after removing expiry. Screenshot refresh now decodes into a separate replacement layer and publishes only after it is ready, retaining the usable layer if opening cancels preparation. The existing conservative four-buffer allowance covers the transient old/replacement snapshot overlap; no persistent stream or history is introduced.

Enter selection previously closed with `commitScrollOffsets: false`, inadvertently disabling the reverse zoom even for unchanged native frames. Visual handoff eligibility now depends on animation settings, viewport alignment and verified native geometry independently of the scroll-commit policy. The owned native test invokes the actual Enter selection handler and asserts that the surface remains attached during closing before the panel disappears. It failed before the correction.

A recorded workspace change exposed a separate closing limitation: projection updates intentionally discard the opening scene, leaving Enter with no reverse scene. Closing now attempts a short Core Animation scene made from the compact previews already displayed for the new active workspace. Native owner and geometry must match the computed targets within two points; otherwise the normal immediate close remains available. Images are reused and released with the closing panel, with no new screenshot, persistent stream or frame history. Compact previews can appear softer at native scale. `overviewPreviewClosings` reports this path. The owned native regression now navigates between two workspaces, updates the active snapshot, selects the destination and asserts a retained closing scene followed by panel removal without native geometry mutation; it failed before this correction. Real-window validation remains necessary for timing and fidelity.

## Overview navigation rendering work (2026-10-03)

An Animation Hitches/Time Profiler capture of the installed daemon showed repeated
AppKit typesetting and application-icon representation resolution in card drawing,
and a 33 ms polling task refreshing a fixed opening scene. The one-shot scene now
retains its original image set without a refresh task; projection changes still
invalidate it, and native bounds are checked before reverse zoom.

Card titles use decoded bitmaps cached by window, text, font size, available width,
and backing scale, with a strict 4 MiB budget. Icons resolve to small 48 px bitmaps
once rather than repeatedly drawing application icon representations. Trackpad
and horizontal drag deltas accumulate immediately, but their latest viewport is
projected once per monitor display-link callback, including the final event.

The same owned native renderer benchmark (140 warm, position-changing frames)
measured mean drawing time from 2.02 ms to 1.21–1.27 ms and p95 from 2.49 ms to
1.44–1.59 ms. This measures drawing work, not presented FPS, and does not establish
a universally stable 120 FPS. The native regression also feeds 100 precise scroll
events before yielding, checks that they are coalesced, and verifies the final
